# ADR 0030: Drive The SSD1306 With A Small In-Tree Async Driver

- Status: Accepted
- Date: 2026-11-14

## Context

Since the 2026-09-28 audit, two unmaintained crates have stayed in
`Cargo.lock`, and `cargo deny` ([auditing](../code-quality.md#auditing))
ignored their advisories by ID:

| Crate | Advisory | Chain |
| --- | --- | --- |
| `proc-macro-error 1.0.4` | `RUSTSEC-2024-0370` (unmaintained) | `maybe-async-cfg 0.2.4`, which `ssd1306 0.10.0` pins with `=0.2.4` |
| `bare-metal 0.2.5` | `RUSTSEC-2026-0110` (deprecated) | `cortex-m 0.7.9`, which bt2usb, Embassy, `nrf-pac`, `nrf-softdevice`, and `panic-probe` use |

`proc-macro-error` runs only inside the compiler, but it is still code from an
abandoned crate that runs on every build machine, and it held an advisory
ignore open with no upstream end in sight. No `ssd1306` release can drop it:

- `ssd1306` 0.10.0 is the latest release (crates.io index, checked
  2026-11-14), and its main branch still pins `maybe-async-cfg =0.2.4`
  (commit `79cb629`, checked 2026-10-10).
- `maybe-async-cfg` 0.2.5 replaced `proc-macro-error` with `manyhow`, but it
  generates the async variants differently: `ssd1306` with the pin raised
  fails to compile with 19 errors (tried 2026-10-10 on a patched copy).
- The crate's whole async API is generated by that macro from its blocking
  code, so a port means rewriting the crate's `maybe_async_cfg` annotations
  and waiting for a release that carries it.

What the bridge needs from a display driver is small. [display.rs](../../src/ui/display.rs)
used `ssd1306` for one panel (128×64, `DisplaySize128x64`), one rotation
(`Rotate0`), one addressing mode (horizontal), buffered graphics mode with
`clear_buffer` before every frame (so every flush sent the whole frame), and
display on/off. It used no terminal mode, no brightness changes, no
scrolling, no SPI, and no partial updates. The driver stack it pulled in was
`ssd1306`, `display-interface`, `display-interface-i2c`,
`display-interface-spi`, `byte-slice-cast`, `maybe-async-cfg`,
`proc-macro-error`, `proc-macro-error-attr`, `pulldown-cmark`, `unicase`, and
`version_check`: eleven crates for about forty lines of protocol.

The protocol is fixed by the SSD1306 datasheet (Solomon Systech, rev 1.1):
an I2C write starts with a control byte; `0x00` (Co=0, D/C#=0) makes every
following byte of the write a command, `0x40` (Co=0, D/C#=1) makes every
following byte display data (section 8.1.5.2). The command set and its
argument counts are in section 9, the addressing modes in section 10.1.

`bare-metal` has no such route. `cortex-m` 0.7.10, the latest release
(crates.io index, checked 2026-11-14), and the `master` branch of
`rust-embedded/cortex-m` (the `cortex-m` crate's manifest there, version
0.7.10, read 2026-11-14) both still depend on `bare-metal` 0.2. No 0.8 is published.
`cortex-m` declares `links = "cortex-m"`, so one image can hold only one
version, and every Embassy crate and `nrf-softdevice` the firmware uses
depend on 0.7. Replacing `cortex-m` would mean replacing Embassy's Cortex-M
support, and the crate supplies the `Mutex` and `CriticalSection` types that
the executor, the HAL, and the SoftDevice bindings share.

## Decision

Replace the `ssd1306` crate with a small async driver in
[ui/ssd1306.rs](../../src/ui/ssd1306.rs), keep the panel configuration byte
for byte, and keep the `bare-metal` ignore, documented by ID with its chain
and removal trigger.

- **Scope.** One panel (128×64 at `0x3C`, mounted with segment remap and the
  remapped COM scan), horizontal addressing, a full-frame flush, and display
  on/off. Anything else (another size, rotation, address, brightness, partial
  updates) is a code change to this module, not a configuration option.
- **Configuration.** `INIT` is one command stream of 26 bytes with the same
  values, in the same order, as `ssd1306` 0.10.0's
  `init_with_addr_mode(Horizontal)` for `DisplaySize128x64`, `Rotate0`, and
  `Brightness::NORMAL`, recorded from that crate with a logging bus before it
  was removed:

  | Bytes | Command (datasheet section 9) | Value |
  | --- | --- | --- |
  | `AE` | Display off | Panel dark while it is configured |
  | `D5 80` | Display clock | Oscillator 8 (reset value), divide by 1 |
  | `A8 3F` | Multiplex ratio | 64 |
  | `D3 00` | Display offset | 0 |
  | `40` | Display start line | 0 |
  | `8D 14` | Charge pump | On: the module has no external VCC |
  | `20 00` | Memory addressing mode | Horizontal |
  | `DA 12` | COM pins | Alternative configuration, no left/right remap (128×64) |
  | `A1` | Segment remap | Column 127 drives SEG0 |
  | `C8` | COM scan direction | COM63 to COM0 |
  | `D9 21` | Pre-charge period | Phase 1 = 1, phase 2 = 2 DCLK |
  | `81 5F` | Contrast | `0x5F` |
  | `DB 40` | VCOMH deselect level | `0x40`, what `ssd1306` calls `Auto` |
  | `A4` | Entire display on | Off: show RAM |
  | `A6` | Normal or inverse | Normal |
  | `2E` | Scrolling | Off |

  The one difference is the end: the old `init` finished with display on
  (`AF`), and `display.rs` had to turn the panel off again at once. `INIT`
  leaves it off.
- **Initialization.** `Ssd1306::init` sends `INIT`, then a blank frame. The
  panel stays dark until `render` has sent the first real frame and turns it
  on, so the panel never shows its power-up RAM ([ADR 0024](0024-renode-oled-models.md)'s
  noise check) or the blank clear. Because `INIT` starts with display off, a
  re-initialization after a fault also darkens a panel that was still lit
  before it clears RAM. In `render` the first frame rewrites all of RAM
  before the panel lights, so the clear is redundant there; it is kept so
  that `init` is safe on its own for a caller that lights the panel next, as
  the self-test does (`init`, display on, then Home), and it costs one frame
  time (about 93 ms) per initialization, not per frame.
- **Framing.** Three kinds of write, each one I2C `write` operation (one
  START, the address, the bytes, one STOP): the configuration stream, the
  window stream `00 21 00 7F 22 00 07` (columns 0 to 127, pages 0 to 7), and
  the frame as one data stream of 1,025 bytes. The window goes out before
  every frame, so the RAM pointer starts at column 0, page 0 even when an
  earlier write was cut short by a STOP or a NACK.
- **Framebuffer.** `Framebuffer` holds the frame as the write that sends it:
  the `0x40` control byte followed by the 1,024 bytes of display RAM in
  horizontal order (page 0's 128 columns, then page 1, and so on; pixel
  (x, y) is bit `y % 8` of byte `(y / 8) * 128 + x`, the same layout
  `ssd1306`'s buffered mode used). The flush is therefore one contiguous RAM
  buffer that EasyDMA reads in place. It implements `embedded-graphics`'s
  `DrawTarget` with `Infallible` errors and ignores pixels off the panel.
- **Bus contract.** The driver is generic over `embedded_hal_async::i2c::I2c`
  and returns the bus error of the first write that fails, sending nothing
  after it. The display task still wraps TWIM0 in `StopSafeI2c` and runs
  each render under `finish_or_stop` ([ADR 0009](0009-isolated-display-task.md));
  both assumptions hold because every transfer is a write-only `LASTTX_STOP`
  transfer and every buffer is either the TWIM copy buffer or the
  framebuffer, which outlive the transfer.
- **Copy buffer.** The constant streams sit in flash, which EasyDMA cannot
  read, so `embassy-nrf` copies them into the 64-byte RAM buffer
  `new_twim` gives the driver. A compile-time assertion in `display.rs`
  keeps `INIT` (26 bytes) and the window (7 bytes) within it.
- **`bare-metal`.** The `RUSTSEC-2026-0110` ignore stays in
  [deny.toml](../../deny.toml), the only one left, with its chain and its
  removal trigger: a `cortex-m` release without `bare-metal` that Embassy and
  `nrf-softdevice` accept, adopted through a dependency upgrade. Dependabot's
  weekly Cargo check proposes such a release when it appears.

## Alternatives Considered

- **Keep both ignores until upstream releases remove the crates.** No release
  path exists for `ssd1306`: its main branch has not moved off the exact pin,
  and `proc-macro-error` would stay on every build machine indefinitely.
  Rejected for `proc-macro-error`; it is the decision for `bare-metal`,
  where the alternative is replacing the Cortex-M runtime under Embassy.
- **Port `ssd1306` to `maybe-async-cfg` 0.2.5 and offer it upstream.** It
  would help other users, but the ignore would stay until a release carried
  the port, on the maintainers' schedule, and bt2usb would keep eleven
  crates for one code path. It can still be done independently.
- **Vendor a patched `ssd1306`.** A `[patch]` copy would drop the advisory at
  once but would carry the crate's terminal mode, SPI interface, rotations,
  and sizes as code to review and keep building, plus the macro rewrite
  itself, for features the bridge does not use. [ADR 0007](0007-vendored-softdevice-patch.md)
  reserves vendoring for a minimal patch to a crate that cannot be replaced.
- **Another SSD1306 crate.** It would trade one external driver for another
  of wider scope, keep code the bridge does not use, and need the same review
  of its I2C framing against `StopSafeI2c`'s assumptions, for no fewer
  dependencies than the module this ADR adds.
- **Write the frame in 16-byte chunks as before.** `display-interface-i2c`
  sent 64 data writes of 17 bytes per frame. One 1,025-byte write is what the
  datasheet's data stream allows, takes fewer bus bits (no repeated START and
  address per chunk) and fewer interrupts, and needs no stack copy. EasyDMA's
  `MAXCNT` on the nRF52840 is 16 bits, so the length is well within it.
- **Send each command as its own write, as before.** Equivalent on the
  panel; one stream is one transfer instead of seventeen and is what the
  datasheet's Co=0 command stream is for.

## Rationale

The driver is the smallest code that does what the bridge does, and every
byte it sends is checked twice: against the datasheet and the recorded output
of the crate it replaces on the host, and against the Renode SSD1306 model
when the real display task runs on the simulated MCU. Keeping the
configuration identical means the panel behaves on hardware as the
previous driver configured it; the framing changes (one command stream, one
data stream) are what the datasheet specifies and what the Renode model
already decoded. Removing the crate also removes ten others and the
`proc-macro-error` ignore, which leaves the audit with a single, explained
exception whose removal trigger is outside bt2usb's control.

## Consequences

Positive:

- `Cargo.lock` no longer selects `proc-macro-error`, `maybe-async-cfg`,
  `ssd1306`, or the `display-interface` crates (11 crates removed), and the
  audit ignores only `RUSTSEC-2026-0110`.
- The release firmware is 5,536 bytes smaller in flash and 296 bytes smaller
  in static RAM, and the self-test 4,232 and 320 bytes (release builds of
  this change against its parent).
- A frame takes about 93 ms at 100 kHz instead of about 105 ms, and a render
  that initializes the panel is six writes (configuration, window, blank
  frame, window, frame, display on) instead of 152.
- The protocol is in the pure core ([ADR 0003](0003-pure-core-and-task-shell.md))
  with ten host tests, so a changed command byte, a wrong pixel layout, or a
  panel lit before its RAM is cleared fails `cargo test`, not only the
  simulation.

Negative:

- bt2usb now owns an SSD1306 driver. A different panel (SH1106, 128×32, a
  module at `0x3D`, another orientation) needs this module changed rather
  than a different constructor.
- The single 1,025-byte data write has not yet run on a real panel. The
  datasheet allows a data stream of any length after one control byte, and
  `ssd1306`'s configuration is unchanged, but the board's OLED checks are the
  proof.
- `syn` 1 stays in the graph: `nrf-softdevice-macro` uses it through
  `darling` 0.13, so this change does not remove it.
- The `bare-metal` ignore remains until upstream `cortex-m` moves.

### Verification Status

- **Implemented:** everything above.
- **Software-verified:** the ten driver tests and the rest of the host suite
  (511 tests) pass; Clippy with `-D warnings` passes for the host, the
  firmware, the firmware with `log-sensitive-data`, and the simulation; the
  three Renode test cases pass with Renode 1.16.1 on Linux, including every
  screen read back from the modelled panel, no power-on noise at boot or
  after the panel is unplugged and reset, and recovery after an address NACK;
  `cargo deny --locked check` passes with one ignore and fails with
  `RUSTSEC-2026-0110` named when that ignore is removed
  ([2026-11-14 record](../validation-records.md#validation-record--2026-11-14-in-tree-ssd1306-driver)).
- **Hardware-verified:** not yet. The
  [self-test](../first-flash.md#2-self-test-image)'s `oled i2c` and
  `oled render` stages and the
  [degraded display checks](../first-flash.md#6-device-management-and-degraded-display)
  on a board are the evidence still needed.
